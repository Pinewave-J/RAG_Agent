# python-rag —— 知识问答 agent 的 Python 复刻版

这是项目根目录那个 Node 版 RAG 系统的 **Python 实现**，用来看清"同一套检索逻辑换一种语言写出来长什么样"。

它不是"重写一个更好的版本"，而是**一份逐位对账过的对照实现**：
分词、切分、BM25、RRF、覆盖率闸门这五个环节的输出，与 Node 版**完全一致**（226 项检查全绿）。

配套教学材料：项目根目录的 `20260918RAG技术学习教程.html`，其中**第 10 章「Python 复刻路线」**专门讲这份代码。

## 三步跑起来

```bash
cd python-rag

# 1) 装依赖（检索部分其实零依赖，装了才能调模型）
pip install -r requirements.txt

# 2) 从 ../knowledge 建索引
python build_index.py

# 3) 只做检索（不联网、不花钱）—— 先跑这一步
python ask.py "总监理工程师应履行哪些职责" --no-llm
```

想完整走一遍（含调模型）：

```bash
python ask.py "监理投标文件由哪几部分组成"
```

Windows 上最省事的做法是**双击 `run-demo.cmd`** —— 它会依次跑完
建索引 → 放行 → 拦截 → 排名翻转四步，**全程不调用大模型**。

### 环境要求

- **Python 3.10+**（用到了 `dict | None` 这类写法）
- 第三方包：`requests`（调模型）、`jieba`（只有 exp3 用）
- 可选：`pypdf` / `python-docx`（只有要读 PDF/Word 时才需要，在 `requirements.txt` 里注释着）

### 配置

`config.py` 按这个顺序找配置：

1. `python-rag/.env` —— 只影响 Python 版
2. `../.env`（项目根目录）—— **Node 版正在用的那份，会直接复用**

也就是说：**如果 Node 版已经跑起来了，这里一行配置都不用改。**

想让 Python 版单独用另一个模型，复制 `python-rag/.env.example` 为 `python-rag/.env` 再改。

查当前生效的配置（排查"为什么没生效"的第一现场）：

```bash
python ask.py --config
```

## 几个必须知道的点

### 1. 混合检索要先单独生成向量

`build_index.py` 默认**不生成向量**（要联网、要花钱、而且慢）。
关键词模式功能完整，所以默认路径必须能在零配置下跑通。

想要混合检索：

```bash
python build_index.py --embed        # 实测：94 条 × 1024 维，落盘 376 KB
python experiments/exp4_vector_rescue.py
```

### 2. 换了分词器就必须重建索引

索引里的 `df` 和词频都是按旧分词器算出来的。不重建就等于拿一份过期统计表去查新词 ——
**不会报错，只会慢慢答不准**。

### 3. `run-demo.cmd` 必须保持纯 ASCII

`cmd.exe` 按**系统 ANSI 代码页**（中文 Windows = GBK）解码 `.cmd` 文件，
**与文件实际存储编码无关**。中文注释若以 UTF-8 存 → 乱码 → `rem` 失效、
`for /f` 引号被撑破 → 整个脚本解析崩溃。
**`chcp 65001` 救不了**（它只改标准输入输出，不改脚本解码）。

所以：**所有中文输出都放在 `demo.py` 里，`.cmd` 只负责选解释器并调用它。**

### 4. 为什么脚本里要设 `PYTHONUTF8=1`

中文 Windows 的默认文本编码是 GBK。打印到真实控制台通常是好的（Python 走宽字符 API），
**一旦输出被重定向或管道，Python 就会退回 GBK**，遇到 `›`（章节路径分隔符）这类字符
直接抛 `UnicodeEncodeError`。设了 `PYTHONUTF8=1` 就整类问题消失。

### 5. `ask.py --no-llm` 是调优时最该反复跑的东西

它把"检索到了什么、覆盖率多少、闸门放没放行"全部打出来，**完全不依赖大模型**。
排查"为什么答不准"时，这一屏比看模型回答有用得多 ——
资料检索对不对，在这里一目了然。

## 对账机制

```bash
python check_parity.py
```

它会读 `reference/reference.json`，把 Python 版的输出与它逐项比对。

基准数据是这么来的（**注意是谁跑的**）：

```bash
node python-rag/reference/gen-reference.js
```

这个脚本调用的是**项目里真实的代码** —— 真正的 `chunker.js`、真正的
`store.rebuildStats()`、真正的 `retriever.js`，输入就是 `knowledge/` 那 4 份 .md。

**为什么必须这样？** 如果基准是我"照着手算出来的"，那它只能证明
"我的理解和我的实现一致"，属于自说自话。让 Node 的原实现产出基准，
才能证明**两套实现对同一个输入给出同一个输出**。

这个说法有个可检验的推论：重跑一遍 `gen-reference.js`，产出的文件应当与
仓库里那份**逐字节相同**（37715 字节）。实测如此。

### 但基准本身也会过时 —— 所以有 `--check`

```bash
node python-rag/reference/gen-reference.js --check
# ✅ python-rag\reference\reference.json 与当前真实代码逐字节一致（37715 字节）
```

它用**当前代码**重算一遍，和盘上的文件逐字节比，不一致就退出码 1。
只读不写。

**为什么必须有这一步：** 对账"全绿"有两种可能，只有一种是好消息。

| 情况 | 危害 |
| --- | --- |
| 两版实现确实一致 | —— |
| **基准已不代表真实代码**（过时 / 被人手改） | `check_parity.py` 成了拿旧尺子量东西：它报的绿是假的，**报的红也是假警报**，会把你推去改一个本来正确的实现 |

尤其是第二种里的"手改基准去迁就错误实现"——那等于把对账机制本身废掉。
所以 `--check` 失败时会把两种原因分开讲：**"代码被改过"和"基准被手改过"
是性质完全不同的两件事。**

实践规则：**动过 `server/` 下任何跟检索相关的文件，或打算相信 `check_parity.py` 的结果，
就先跑一次 `--check`。**

对账覆盖 8 组、226 项：

| 组 | 比什么 | 为什么这一项会不一样 |
| --- | --- | --- |
| ① | 分词：token 逐个相同（连顺序） | 顺序错了 BM25 分数不变，但 `queryTerms` 的展示会变 |
| ② | 切分：片段数 / 每片长度 / 内容校验和 | 长度差一个字符，就是 `\r\n` 还是 `\n` 这种跨语言差异 |
| ③ | 索引统计：`avgdl` / 词表规模 | 标题加权有没有算、算了几轮，全在这个数字里 |
| ④ | 5 个查询的完整结果（模式 / 覆盖率 / 闸门词 / top5） | 端到端：前面任何一环偏了这里就会不一样 |
| ⑤ | 标题权重 0 / 0.25 / 0.5 / 1.0 四档的排名与覆盖率 | 盯"修好之后到底排第几"，防止改动悄悄吃掉修复效果 |
| ⑥ | RRF 三场景的排名与归一化分数 | `1/(k+rank+1)` 里那个 `+1` 最容易漏 |
| ⑦ | 余弦相似度（含零向量） | 除零怎么处理，两种语言默认行为完全不同 |
| ⑧ | idf 与停用词表的具体行为 | 钉死"双字轮不查停用词"这个反直觉的实现细节 |

### 踩过的坑：对账第一次跑，222 项里挂了 1 项

唯一挂掉的是长度检查：

```
03-建设工程监理规范GBT50319-2013.md
  Node   29388 字符
  Python 28061 字符
  差 1327
```

原因不是算法，是**读文件的方式**：Python 文本模式默认开启「通用换行」，
会把 `\r\n` 悄悄改写成 `\n`，每个换行少一个字符 —— 这份资料有 1327 个换行，
于是正好少 1327 个字符。Node 的 `readFileSync` 则原样保留。

修法（`loaders.py`）：

```python
with open(path, 'r', encoding='utf-8', newline='') as fh:
    return fh.read()
```

**这个坑最值得记住的是：它完全不会报错。** 1327 个字符的差别不会让任何测试变红，
只会让片段边界比另一版微妙地偏一点点。

### 对账的意外收获

写 Python 版时你必须逐行判断"注释说的和代码做的是不是一回事"，
否则不知道该照哪个实现。于是发现了一处**注释与代码不同步**：
`pickSectionTokens` 上方的注释写着"按**从后往前**取"，
而代码实际是分组后**从前往后**取。这种问题在单语言阅读时几乎永远不会暴露。

### 反过来，Node 侧也改了两个地方

**移植不是单向的抄写。** 为了让 `gen-reference.js` 能用上"真模块"，
Node 侧被改了两处 —— 两处都是**向后兼容**的，无参调用的行为一个字节都没变
（`npm run test:retriever` 26 项、`check_parity.py` 226 项改完仍全绿）。

| 位置 | 改动 | 为什么非改不可 |
| --- | --- | --- |
| `server/store.js:121` | `rebuildStats()` → `rebuildStats(opts = {})`，接受 `sectionTfWeight` 覆盖标题权重 | 权重原本是模块级常量，**从外面根本改不动**。而基准要跑 0 / 0.25 / 0.5 / 1.0 四档扫描，否则 `SECTION_TF_WEIGHT = 0.5` 那 20 行注释就只能被人**相信**，无法被人**检验** |
| `server/retriever.js:284` | 导出 `fuseRRF` | RRF 夹具要用"人造排名"去撞击这个纯函数。走完整的 `search()` 是撞不准的 —— 那里还混着 BM25 打分和闸门，一旦对不上你分不清是谁的错 |

**这值得单独记一笔**：Python 版最初把 `title_weight` 做成函数形参，
而 Node 版是常量 —— 当时这被当成一个"Python 更好改"的对照。
结果写基准生成器时反过来被逼着给 Node 版也加上了同样的参数。
**你会被迫重新审视原代码里每一处"只能靠信"的地方，因为轮到你自己去验证时，它们就挡路了。**

| 项目 | 状态 | 说明 |
| --- | --- | --- |
| 加载 / 切分 / 分词 / 索引 / 检索 / 闸门 / 生成 | 已完成 | 226 项对账全绿 |
| 命令行问答 + 流式打印 | 已完成 | 实测跑通：检索 5 条、覆盖率 0.7084、带 `[1]` 角标 |
| 关键词模式（零配置零依赖） | 已完成 | 不填任何密钥就能完整工作 |
| 混合检索（BM25 + 向量 + RRF） | 已完成 | 需 `build_index.py --embed` |
| 增量导入 | **未做** | Node 版的 `upsertDocument()` 实现了它；这里每次全量重建（94 片段 29ms，够用） |
| 前端界面 / HTTP 接口 | **未做** | 它不是 RAG，是平台特性；命令行 + 流式打印替代了它 |
| SSE 路由层 | **未做** | 解决的是"一个 HTTP 连接怎么持续推数据"，属于 Web 框架问题 |
| 扫描件守卫的完整判定 | 简化版 | 节点逻辑一致，但阈值只保留了"独立内容 < 300 字"这一条决定性判据 |
| PDF / Word 解析 | 可选 | 在 `requirements.txt` 里注释着，用到再装 |

**为什么要把"没做什么"列出来？** 因为一份移植代码最容易被误用的方式，
就是**以为它和原版一样完整**。把边界写清楚，你才知道哪些地方可以照抄、哪些要自己补。

## 改代码前值得知道的

- **`retriever.py` 的 `search()` 是同步函数**。Node 版曾经把 `searchVector()` 写成
  `async`，导致同步调用方拿到 Promise 而不是数组 —— 这个坑在 Python 里同样存在
  （会得到 coroutine 对象，`len()` 直接报错）。加检索通道时，新函数也必须是同步的。
- **`SECTION_TF_WEIGHT = 0.5` 和 `SECTION_TF_MAX_TOKENS = 24` 不要随手改。**
  `bm25_index.py` 顶部有几十行注释讲清了原因（`履行` 正好落在第 18 位，
  上限压到 16 就会把它挤出去）。改完记得跑 `check_parity.py` —— **它应该变红**，
  变红说明它真的在盯着业务逻辑。
- **`coverage_of()` 读的就是 `chunk_tf`**，而 `chunk_tf` 已经含标题加权。
  这是刻意的：否则会出现"打分认了标题、闸门却不认"的口径分裂。
- **造测试数据别用"同一句 + 变数字"**，正常资料的形态是"每条表述都不同"。
