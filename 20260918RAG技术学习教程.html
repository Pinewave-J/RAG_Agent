01RAG 到底是什么

一句话：让大模型开卷考试，而不是闭卷默写。

先讲清两个基础概念。

大模型（LLM） 这类东西，你可以把它想成一位读了很多书、但刚入职的同事：文笔极好、什么都能聊， 但他不知道你们公司内部的规章制度，而且有个致命习惯 —— 不知道的时候不会说"我不知道"，而是编一个听起来很像的答案。 这个毛病有个专门的名字，叫 幻觉。

02项目整体架构

先看地图再走路。这个项目只有十几个文件，没有数据库、没有前端框架、没有构建步骤。

它是什么：一个 Node.js 单进程服务。同一个端口同时对外提供两样东西 —— 网页（public/ 里的 HTML/CSS/JS）和 接口（/api/...）。 资料存在硬盘上的两个文件里：data/kb-index.json（片段正文）和 data/kb-vectors.bin（向量，当前没启用）。就这些。

没有数据库是这个项目最容易让人意外的地方。 142 个片段、5.8 万字，全量常驻内存，检索就是一次内存里的数组循环 —— 所以整个检索耗时是毫秒级的。 当你的知识库在几万片段以内时，这种"土办法"比装 Elasticsearch 划算得多。

03加载：把文件变成文字

RAG 的第一步，也是最朴素的一步：不管你上传的是 PDF 还是 Word，先把它变成一坨纯文本。

要解决什么问题

用户的资料形态千奇百怪：.md、.txt、.pdf、.docx、.html…… 但后面的所有环节（切分、分词、检索）都只认识纯文本。 所以需要一个"翻译层"，把各种格式统一成 string。业界管这一步叫"文档解析/抽取（parsing / extraction）"。

项目里干这件事的文件是 server/loaders.js，总共 155 行。它的入口长这样：

server/loaders.js:89入口函数
async function extractFromFile(filePath) {
  const ext = extOf(filePath);

  if (PDF_EXT.has(ext)) return extractPdf(filePath);
  if (DOCX_EXT.has(ext)) return extractDocx(filePath);

  const raw = fs.readFileSync(filePath, 'utf8');

  if (HTML_EXT.has(ext)) return stripHtml(raw);
  if (ext === '.json') {
    try {
      return JSON.stringify(JSON.parse(raw), null, 2);
    } catch {
      return raw;
    }
  }
  return raw;
}

逐行读一遍：

代码在干嘛
const ext = extOf(filePath)取扩展名并转小写。先判断类型，再决定用哪把"钥匙"开这个文件。
PDF_EXT.has(ext)PDF 和 DOCX 是二进制格式，直接按文本读全是乱码，必须交给专门的解析库。
fs.readFileSync(filePath,'utf8')剩下的格式本质就是文本文件，直接读。注意第二个参数 'utf8'：不写它拿到的是 Buffer（字节），写中文会变乱码。
stripHtml(raw)HTML 里全是 <div> 这类标签，是给浏览器看的，不是给模型看的，得剥掉。

关键概念①：可选依赖，让"没装库"不等于"服务起不来"

PDF 解析需要 pdf-parse，Word 解析需要 mammoth。 这个项目把它们放进了 package.json 的 optionalDependencies，而且不是在文件顶部 require， 而是等到真正要解析时才加载：

server/loaders.js:58懒加载 + 友好报错
function requireOptional(pkg, hint) {
  try {
    return require(pkg);
  } catch (err) {
    const error = new Error(
      `缺少可选依赖 ${pkg}，无法解析该格式。请执行：npm install ${pkg}（${hint}）`
    );
    error.code = 'MISSING_OPTIONAL_DEP';
    error.cause = err;
    throw error;
  }
}
✅

这是一个可以直接抄走的设计模式。把非核心依赖做成"用到才加载"， 好处有两个：一是启动更快（不用在启动时加载所有解析器）；二是报错更友好 —— 用户看到的是"请执行 npm install pdf-parse"，而不是一句 Cannot find module 'pdf-parse' 就没了。

想想看：如果写成文件顶部的 const pdfParse = require('pdf-parse')， 而这个库恰好没装，会怎样？整个服务直接起不来 —— 一个只用来传 PDF 的库，把所有功能全拖下水。

关键概念②：docId —— 给每份资料发一张"指纹身份证"

知识库要支持"重新上传同一份文件不产生重复"。怎么判断两次上传的是不是同一份资料？ 靠内容指纹：

server/loaders.js:30核心
function makeDocId(filename, content) {
  const hash = crypto.createHash('sha1');
  hash.update(path.basename(String(filename || 'untitled')).toLowerCase());
  hash.update('\u0000');
  hash.update(content ? String(content) : '');
  return hash.digest('hex').slice(0, 16);
}

哈希 是这里的核心。把它想成榨汁机：同样的水果榨出来的汁必然一样，换一种水果汁就完全不同， 而且没法把汁还原成水果。项目用的是 SHA-1， 取前 16 位作为身份证号。

注意一行容易被忽略的写法：hash.update('\u0000')。 它往文件名和内容之间塞了一个不可见的空字符作为分隔符。没有它会怎样？ "ab" + "c" 和 "a" + "bc" 会算出同一个 ID —— 两个完全不同的文件撞在一起。这是个经典的"拼接歧义"陷阱。

关键概念③：先体检，再入库

这一步是这个项目里最有价值的工程经验，也是多数教程不会讲、但真实项目一定会踩的坑。

问题出在 PDF 上。pdf-parse 只能读 PDF 的文字层。 如果用户传的是一份扫描件（整页就是一张图，没有文字层），解析器不会报错 —— 它会"尽力而为"地返回它能读到的内容：每页的页眉、页脚、水印。 结果就是同一句话在全文里重复几十遍，而有效正文一个字都没有。

⚠️

如果这种内容进了知识库会怎样？它会被切成几十个几乎完全相同的片段。 由于这些片段里含有"信息公开""浏览专用"之类的词，它们会在检索时频繁抢到前排位置， 却提供不了任何有用信息 —— 这就是纯噪声，会挤掉真正有用的片段。 最糟的是：系统一切正常，没有报错，你只会觉得"这破系统怎么老是答不准"。

所以项目在文本入库前加了一道体检（server/ingest-guard.js，245 行）， 它同时看三个信号，任何一个命中就拒绝入库：

信号怎么判定对应真实场景
跨行短语重复同一个 8 字短语出现 ≥8 次，且占全文 ≥50%文字层把 N 个页眉合并成了一整行，行级去重抓不到
行级重复单一重复行 ≥50%，且独立内容 <200 字页眉每页各占一行，格式规整
可读性字母/数字/汉字占比 <15%字体缺少 Unicode 映射，解析出来全是乱码

但光有"重复率高"还不够。正常资料里也会反复出现相同句式（比如每条都写"投标人应当……"）。 所以真正的决定性判据是这一条 —— 看重复块之外还剩下多少独立内容：

//   正常资料：即使句式反复（每条都写"投标人应当…"），
//             重复块之外仍有成百上千字的独立表述。
const independentChars = Math.max(0, compact.length - phrase.count * phrase.blockChars);

if (
  phrase.count >= MAX_PHRASE_REPEATS &&
  phrase.share >= 0.5 &&
  independentChars < MIN_INDEPENDENT_CHARS     // 300 字
) {
  return { scanned: true, reason: `...重复了 ${phrase.count} 次...` };
}

04切分：把长文切成片段

这是整条链路里最影响效果、又最容易被忽视的一步。切得好，检索就准；切坏了，后面怎么调都救不回来。

为什么要切？两个硬约束

约束一 · 装不下

模型一次能处理的文字有上限，这个上限叫 上下文窗口。 一份 20 万字的规范整份塞进去，既装不下，也极贵（按量计费）。

约束二 · 找不准

一整份资料作为检索单位，结果只能是"这份资料相关"—— 太粗糙了。切成小块之后，才能定位到"第 3.2.1 条相关"。

所以切分的本质是：在"每块足够小装得下"和"每块足够完整说得清一件事"之间找平衡。这是 RAG 里最需要靠实测调参的地方。

第三步：重叠（overlap）—— 为什么相邻片段要"重复一点"

假设原文是：「…… 投标保证金的退还时间，一般为中标通知书发出后 5 日内…… 」

  • 片段 A 结尾：「……投标保证金的」

05分词与索引：BM25 的原料

要让程序"按内容找资料"，第一步得把句子拆成词 —— 这就是分词。这一步做不好，后面所有检索都是白搭。

为什么中文分词是个麻烦事

英文天然有空格：bid bond refund 一眼就知道是三个词。 中文是连成一串的：「投标保证金什么时候退还」—— 计算机怎么知道要切成「投标 / 保证金 / 什么时候 / 退还」？

主流做法有两类：① 装一个专业分词库（如 jieba，带词典和统计模型，准但没有词典的新词会切错，而且要本地编译）； ② 用简单规则切。项目选了第二条路：

「单字 + 相邻双字」方案（业内叫 bigram）。 bigram 的思路很朴素： 中文里绝大多数常用词是两个字，那我就把所有相邻的两个字都当作候选词。

「投标保证金」→ 单字：投 标 保 证 金　双字：投标 标保 保证 证金

它显然会切出一堆垃圾词（标保 根本不是词）。但没关系 —— 真正的词会在很多资料里出现，垃圾词几乎不出现，后面的 BM25 会给它们极低的权重。 这是个"宁可错杀、靠统计量自动纠偏"的实用主义选择：零依赖、跨平台、够用。

function tokenize(text) {
  const norm = normalize(text);
  if (!norm) return [];

  const tokens = [];
  TOKEN_RE.lastIndex = 0;
  let match;
  while ((match = TOKEN_RE.exec(norm)) !== null) {
    const seg = match[0];

    if (isCJK(seg[0])) {
      const chars = Array.from(seg);

      // 1) 单字（过滤虚词）
      for (const ch of chars) {
        if (!STOPWORDS.has(ch)) tokens.push(ch);
      }

      // 2) 相邻双字 bigram —— 中文双字词的主要来源
      for (let i = 0; i + 1 < chars.length; i++) {
        const bi = chars[i] + chars[i + 1];
        // 两个字都是虚词的组合没有信息量
        if (STOPWORDS.has(chars[i]) && STOPWORDS.has(chars[i + 1])) continue;
        tokens.push(bi);
      }
    } else {
      // 英文 / 数字 / 版本号，长度 1 会带来大量噪声，直接丢弃
      if (seg.length >= 2 && !STOPWORDS.has(seg)) tokens.push(seg);
    }
  }

  return tokens;
}

细节为什么这么写
单字轮查停用词表（STOPWORDS.has(ch)）「的」「了」「在」这类字几乎没有区分力，留着只会干扰打分
双字轮只排除"双停用词组合"因为 的+监 组成的「的监」本身就不是词，而 投标 这类双字必须留下 —— 这轮不能查停用词表
英文/数字长度 1 丢弃单个字母（如 a）和单个数字到处都是，全是噪声

「什么」「哪些」「怎么」这些疑问词，在单字轮会被停用词表拦下， 但它们在双字轮里是合法双字，会原封不动地溜进词表。 如果后面算覆盖率时不过滤它们，那么「XXX是什么」的检索词就会退化成只剩「什么」—— 而"什么"在几乎所有资料里都出现过，于是任何问题都能命中，判断"资料够不够"的那道闸门等于彻底失效。

这个坑的可怕之处在于：它让系统看起来更"聪明"（什么问题都敢答）， 只有当你问一个知识库里根本没收录的东西、它却仍然自信作答时，才会暴露。07 节会看它怎么修。

DF 为什么重要？用一个直觉来理解"词的价签"。 假设你要在人群里找一个人。如果说"找一个戴眼镜的人"，你可能还得挑半天； 如果说"找一个姓欧阳的人"，那你立刻就能锁定。

DF 就是这个词的"大众程度"。DF 越高的词越不值钱（"项目""工作""内容"到处都是）， DF 越低的词越有区分力（"监理""保证金""废标"）。 把这个直觉反过来写成公式，就是下一节的 IDF。

      : [];

    totalLen += chunkLen;

      state.df.set(token, (state.df.get(token) || 0) + 1);

词面检索撞墙的地方

项目 README 里记录了一个实测到的真实例子，非常值得记住：

用户问：「如何申请营业执照」

知识库里有一句话：「……企业资质证书、营业执照、类似工程业绩证明……」

词面完全匹配（"营业执照"四个字都在），覆盖率 100%，闸门放行， 于是模型拿到的资料是"投标要交哪些材料"。但用户问的是"怎么办营业执照"，完全答非所问。

🧱

这不是 bug，是词面检索的原理边界。 关键词检索能判断的是"资料里出现没出现过这个词"， 它没有能力判断"这份资料解释的是这件事吗"。 那句话里没有任何信息能表明"这一页讲的不是怎么办执照"。

关键概念：向量与语义距离

要突破这个边界，得换一种表示方式：把每段文字变成一串数字，让"意思相近的文字， 算出来的数字也相近"。这串数字就叫 向量， 产出它的模型叫 Embedding 模型。

项目里配的默认模型是 text-embedding-v3，输出的向量通常是上千维的 （也就是一千多个数字）。人脑想象不出 1024 维空间，但没关系 —— 我们可以把它压到二维来看个意思：

BM25：不只是"数关键词"

最朴素的关键词打分是"数命中了几个词"。这不够好，因为：

  • 「的」「项目」命中一次，和「保证金」「废标」命中一次，价值完全不同 → 需要 IDF 加权
  • 一个词在一段里出现 10 次，不代表比出现 3 次重要 3 倍 → 需要饱和处理
  • 长片段天然容易命中更多词 → 需要长度归一化

把这三件事写进一个公式，就是 BM25。 项目里的实现在 server/retriever.js:32，核心就三行：

server/retriever.js:47打分公式在循环里
for (const [token, qCount] of queryTf.entries()) {
  const f = tf[token];
  if (!f) continue;                                 // 这段没有这个词，跳过

  const dfi = df.get(token) || 0;
  const termIdf = idf(dfi, N);                      // ① 稀有度：越罕见越值钱
  const qWeight = 1 + Math.log(qCount);             // ② 问题里重复出现的词略加重

  const denom = f + BM25_K1 * (1 - BM25_B + (BM25_B * len) / store.state.avgdl);
  score += termIdf * ((f * (BM25_K1 + 1)) / denom) * qWeight;
  //       ↑ ③ 饱和：f 再大，分数增长也会趋于平缓     ↑ ④ len 归一化
}

公式看着唬人，拆开就四件事：

部分对应代码作用
① IDFidf(dfi, N)稀有词的加分系数。代码里用 log(1 + (N-df+0.5)/(df+0.5))，加 0.5 是为了平滑，保证结果恒为正
② 查询词权重1 + Math.log(qCount)问题里同一个词出现两次，略微加重 —— 但用 log 压一下，避免"重复三次就翻三倍"
③ 词频饱和(f*(k1+1))/(f+k1*…)f 从 1 涨到 10，分数涨得很快；从 100 涨到 110，几乎没有区别。防"复读机"靠堆词频刷分
④ 长度归一化len / avgdl片段越长，分母越大，分数越低。防止长片段靠"词多"占便宜

其中 k1（默认 1.5）控制饱和速度，b（默认 0.75）控制长度归一化的力度。 这两个是 BM25 唯一的两个旋钮：

BM25 调参实验室（真实语料）
k1 词频饱和 1.5
b 长度归一化 0.75

观察这三件事：① 把 b 拖到 0 → 长度不再有任何影响； ② 把 b 拖到 1 → 长片段被强烈压制，短片段容易冒头； ③ 把 k1 拖到 0 → 词频完全失去意义（出现 1 次和 10 次一样）。 真实调参时，先在真实数据上看排名变化，再决定改不改，别凭感觉。

两路检索怎么合：RRF 融合

现在系统有两个通道在找资料：关键词通道（BM25）和语义通道（向量余弦）。 两个通道各自给出一份排名，怎么合成一份最终结果？

最直觉的做法是加权求和：总分 = 0.5×BM25 + 0.5×余弦。 但这里有个量纲问题 —— BM25 分数可能是 8.7，余弦相似度是 0.83， 两者根本不在一个量级上，直接相加等于让 BM25 单方面决定结果。

项目的选择是 RRF 融合： 不看分值，只看排名。

为什么"只看排名"反而更好？因为排名是跨通道可比的。 "在这条通道里它排第 2"这个信息，在 BM25 和向量里含义是一致的； 而"得分 8.7"和"相似度 0.83"毫无可比性。

k 的作用是压平差距：k=60 时，第 1 名得 1/61≈0.0164，第 2 名得 1/62≈0.0161 —— 差距很小。这意味着一条通道的第一名，不会因为"得分高"就压过另一条通道的一致意见； 真正的赢家是"两路都排得靠前"的片段。这就是融合的智慧：让两个通道互相验证。

闸门：判断"知识库到底覆没覆盖"

找到一堆片段之后，系统得先回答一个问题：这些资料真的能回答问题吗？ 如果资料完全不相关，最省钱也最诚实的做法是直接告诉用户"没收录"，连模型都不叫。

项目用了一个可解释的指标：查询词加权覆盖率。

闸门词 = 查询词中满足「长度 ≥ 2」且「不是停用词」且「语料里真存在(df>0)」且「不是每个片段都有(df<N)」的词
覆盖率 = 最佳片段命中的闸门词 idf 之和 ÷ 全部闸门词 idf 之和
判定   = 覆盖率 < 0.34 → 兜底，不调用模型

本章最硬的一块：226 项逐位对账

光看代码觉得"两版差不多"，是没有说服力的。"差不多"和"一模一样"之间， 差着好几个 +1。所以 Python 版配了一套对账机制， 流程是这样的：

对账是怎么做的两步
第一步：让 Node 原版自己跑一遍，把结果存成基准文件
    node python-rag/reference/gen-reference.js
        │
        │  它调用的是项目里真实的代码 —— 真正的 chunker.js、
        │  真正的 store.rebuildStats()、真正的 retriever.js，
        │  输入就是 knowledge/ 那 4 份 .md
        ▼
    python-rag/reference/reference.json      （1389 行，全部是硬数据）

第二步：让 Python 版跑同样的输入，逐项比对
    python check_parity.py
        │
        ▼
    全部通过：226 项检查

第三步（最容易被跳过、也最不该跳过）：回头确认基准本身还是不是真的
    node python-rag/reference/gen-reference.js --check
        │
        │  用当前代码重算一遍，和盘上那份逐字节比
        ▼
    ✅ python-rag\reference\reference.json 与当前真实代码逐字节一致（37715 字节）
🔑

关键在第一句：基准数据必须由被测对象自己生成。 如果基准是我"照着手算出来的"，那它只能证明"我的理解和我的实现一致" —— 自说自话。 让 Node 的原实现产出基准，才能证明两套实现对同一个输入给出同一个输出。

这也是一个通用的做法：移植任何代码之前，先给原版做一个"照相机" —— 把关键中间结果落成 JSON。之后的每一步改动都能立刻验证， 而不是等到最后"感觉不对"再回头查。

⚠️

第三步不能省：对账"全绿"有两种可能，只有一种是好消息。

  • 好的一种 —— 两版实现确实一致。
  • 坏的一种 —— 基准文件已经不代表真实代码了：它过时了，或者被人手改过。 这时 check_parity.py 是拿一把旧尺子在量东西， 它报的绿完全是假的；更糟的是它报的红也可能是假警报， 会把人推去改一个本来正确的实现。

--check 专门拆穿第二种情况： 它用当前代码重算一遍，和盘上那份逐字节比，不一致就退出码 1， 并且把两种原因分开讲清楚 —— "代码被改过"和"基准被手改过"是性质完全不同的两件事， 后者意味着对账机制本身失效了，必须先查清是谁改的、为什么改。

实践上：只要你动了 server/ 下跟检索相关的任何一个文件， 或者打算相信 check_parity.py 的结果，就先跑一次 --check。 它只读不写，1 秒钟的事。

真实踩到的坑：对账第一次跑，222 项里挂了 1 项。 唯一挂掉的是第 ② 组的一项长度检查：

第一次对账的输出实测
03-建设工程监理规范GBT50319-2013.md
  Node   29388 字符
  Python 28061 字符
  差 1327

原因不是算法，是读文件的方式。 Python 用文本模式 open(path, 'r', encoding='utf-8') 打开文件时， 默认开启「通用换行」：它会把 \r\n 悄悄改写成 \n —— 每个换行少一个字符。这份资料里有 1327 个换行，于是正好少 1327 个字符。 而 Node 的 readFileSync(path, 'utf-8') 原样保留 \r\n。

修法只有三个字符：

python-rag/loaders.py修复
with open(path, 'r', encoding='utf-8', newline='') as fh:
    return fh.read()

newline='' 关掉换行转换，Python 才会原样返回字节里的 \r\n。 加完之后 226 项全绿。

这个坑最值得记住的地方是：它完全不会报错。 1327 个字符的差别不会让任何测试变红、不会让检索结果明显变差 —— 它只是让你的片段边界比另一版微妙地偏了一点点。 如果不是有一份"逐位对账"在盯着，这个差异永远发现不了， 而它会在你将来做双语言对照时变成一团看不懂的迷雾。

🔍

对账还有一个副作用，很意外但很有价值：它把"注释和代码不同步"也揪出来了。 第 05 章里已经讲过一例：pickSectionTokens 上方的注释写着"按从后往前取"， 而代码实际是分组后从前往后取 —— 注释描述的是另一个版本的实现。

为什么会发现？因为写 Python 版时你必须逐行判断"注释说的和代码做的是不是一回事"， 否则你不知道该照哪个实现。这种"注释说谎"的情况在长期项目里非常常见， 而单语言阅读时几乎永远不会暴露 —— 你只是读过去，点点头。

所以结论不是"哪个分词器更好"，而是：

换分词器是一个需要重新评估检索质量的改动，不是一次无害的替换。 而且有一条铁律 —— 换了分词器就必须重建索引： 索引里的 df 和词频都是按旧分词器算出来的， 不重建就等于拿一份过期统计表去查新词。它不会报错，只会慢慢答不准。

实验 B · 闸门实验室：一行代码的有无，差别有多大

同一个问题、同一份语料，两个只差一行的闸门版本并排跑。 左边是修复后（会过滤停用词），右边是缺陷版（忘了过滤）。

问题
✓ 修复后（有停用词过滤）
✗ 缺陷版（少了那一行）

请务必用「生造词」那个按钮点一次。 缺陷版的闸门词会退化到只剩「什么」—— 而任何片段都含「什么」， 于是覆盖率恒为 1.0，闸门对所有输入都返回"已覆盖"。

它没有报错、没有异常，数学上还在正常工作， 只是失去了全部判别能力。这就是"放宽式缺陷"为什么最危险： 它让系统看起来更"宽容"（该答的都能答），只有"该拒的没拒"才会暴露 —— 而用户根本不会去试一个明知知识库里没有的问题。

一个说明：这个实验跑的是页面上那 7 条演示语料， 所以覆盖率的具体数值会和 exp2 在 94 片段真实语料上跑出来的不完全相同 （比如「今天上海的天气怎么样」那一问，94 片段里的覆盖率是 0.4672， 这里更高 —— 语料里出现「天气」的片段占比不一样）。 要看的是左右两版之间的差别，不是这几个数字本身。 想看 94 片段上的逐词结果，跑 python experiments/exp2_gate.py。

这一章真正想教你的，其实只有三句话：

① 算法跟语言无关。BM25、RRF、覆盖率，用 Python 写一遍， 跑出来的排名和 Node 一模一样。所以你花在理解机制上的时间不会贬值， 花在记 API 上的时间才会。

② "差不多"值不了钱，"一模一样"才值。 226 项对账里唯一挂掉的那一项，是一个 \r\n 的差别 —— 它不会让任何功能出错，但它说明你以为你懂了的地方，其实还有一个你没注意到的默认行为。

③ 能被推翻的结论才值得信。 这一章里最诚实的两组数据，一个是"换了分词器排名几乎没变"， 另一个是"开了向量反而有一条后退了一名"。它们都没有支持我原来的预期 —— 而这恰恰是它们值得写出来的理由。
